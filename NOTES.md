## Stages 3-4 — scoring + dev shard (2026-09-25)

Built `src/scoring.py` and `src/shard.py`. Full details in `docs/PLAN.md`.

**Recon reconfirmed on the full dataset** (not just the 50k sample): one-to-one holds
with **0 violations across 7,638,365 pairs**, singleton rate **5.58%**
(123,247/2,206,821), mean 3.46 matches per entity, and every matched ID exists in
S2/S3. `src/convert.py` does the full 2.3 GB in 6.9 s locally, so the whole dataset is
workable on a laptop for measurement purposes.

**scoring.py** — macro-F_0.5 via the closed form `1.25*tp / (0.25*|truth| + |pred|)`,
asserted identical to the literal formula. Baselines on full train data:

| Baseline | macro-F_0.5 |
|---|---|
| README worked example | 0.7143 (brief says 0.714) |
| predict-empty everywhere | 0.055848 = the singleton rate exactly |
| perfect oracle | 1.000000 |
| drop 1 true match per entity | 0.815198 |

Split (hash of S1 entity ID, seed 13): 1,765,946 train / 440,875 val, zero straddling.

**Trap:** Polars `write_csv` writes `""` for empty strings; with the spec's
`quote_char=None` that reads back as a 2-char ID and silently zeroes the score.
Stage 9 must use `quote_style="never"`.

**shard.py** — the planned key-space shard was built, measured, and demoted to
non-default. No raw field gives a shard key that agrees between an S1 record and its
true match: leading trigram agrees only **77.3%** of the time over 1M true pairs,
because S1 is 100% Latin while S2/S3 carry 8 Indic scripts (addresses included, ~9%).
Key-space sharding therefore yields **81.7%** ground-truth self-consistency and skews
against India (3.21% kept vs 4.45% US), making the >= 97% blocking gate unevaluable.

Default `--mode s1` instead: hash 5% of S1 entity IDs, keep S2/S3 whole. Full data:
110,227 entities (4.99%), rival-retention ratio **1.0000**, GT self-consistency
**100.00%**, no country skew. Cost scales with S1 count, which is where the pair work is.

**`dataset_sample/` cannot validate sharding** — 97.74% of its GT rows reference an S1
entity absent from its own `train_source1`, since each file was sampled independently.
`shard.py` warns instead of emitting a wrong shard. Sharding is validated on full data.

## Stage 5 + blocking questions answered (2026-09-25)

**Q1 — is transliteration a blocking prerequisite? NO. It is a feature-quality win.**
For the 551,240 GT pairs with an Indic-script S2/S3 side, **0.0%** of the S1 records have
a name token with df <= 1,000 in the S2+S3 index (p10 of the rarest token DF is 8,928;
Latin control: 51.4% below 1k, median 818). These S1 names are generic templates
("Balaji Investment Private Limited"), so transliteration recovers the same common words.
There is no rare name token in either script.

The **address** is the route for them, and it works: 82.2% of Indic-matched pairs have an
S1 address token with df <= 1,000 (51.7% below 100) — better than Latin's 78.2%.

Measured payoff of normalization (token Jaccard vs true match, 30k pairs): Devanagari
0.036 -> 0.198 with the share of pairs sharing *no* token falling 92.8% -> 18.4%; Other
Indic 0.042 -> 0.167, 91.7% -> 33.1%; Latin 0.666 -> 0.714. So stage 5 turns the Indic
name field from useless into usable for stage 7 — which is exactly a feature win.

**Q2 — conjunctive reachability** (a token pair intersecting <= 50 records, df <= 50k,
exact intersections, tokens deduped): Latin **65%** reachable (21% have no pair at all,
13% have pairs that all intersect >50), Devanagari **29%** (70% blocked by all-pairs->50),
Other Indic **99%**. Versus the single-token df<=1k baseline (Latin 64% / Devanagari 0% /
Other Indic 93%), conjunction rescues Other Indic, moves Devanagari off zero, and **barely
touches Latin**.

**Cost** over 2,206,821 S1 records, posting entries touched: naive k=3 at df<=50k is
**59.9e9** — not materialisable. Rarest-first with early termination: 14.0e9. At df<=5,000:
1.0e9, still covering 64.5% of S1 by name. Operating point: rarest-first, df cap ~5,000,
address index for the rest. Coverage binds harder than cost — at df<=1,000, 52.3% of S1
records have no usable name token.

**Built `src/normalize.py`.** 8 Indic scripts by Unicode block -> ITRANS -> unidecode,
one-directional. Anusvara `M`->`n` ("marketimga" -> "marketing") and final-schwa trim
("limiteda" -> "limited"). Legal suffixes incl. French sarl/sas/sasu/eurl/sci/snc; address
abbreviations incl. French street words; house numbers and PIN/ZIP extracted. Two bugs
caught by assertions: a `\W` junk trim eats the final matra off Indic words and the accent
off "Café" — trimming is by Unicode category instead.

**Cost: 9m23s for 12.53M rows at 107% CPU — single-core bound under the GIL.** This is now
the slowest stage by two orders of magnitude (convert 7s, index 10s). Parallelise with
multiprocessing before the full run; it is embarrassingly parallel.

Added the `quote_style="never"` hard rule to CLAUDE.md. Freed regenerable artifacts

## Stage 6 candidate generation (2026-09-25)

caps, not normalization. Measured lever: raising the single-token blocks from df<=200 to

India 81.77%. 2.2% of S1 get zero candidates. Reduction ratio 0.9999976550.

**Model.** LightGBM, 5.02M pairs (12.70% positive), 35 features, GroupKFold(4) by S1.

**Decision layer. Val macro-F_0.5 = 0.847264** (tau=0.25, delta=0.35). The sweep surface
is nearly flat in tau and strongly shaped by delta — with a well-separated classifier the
question is how many to accept, not whether. One-to-one resolution worth +0.00185.

**Leak caught mid-run.** features.py filtered the fold in SQL with DuckDB's `hash()`,
while scoring.py defines the split with Polars' `hash(seed=13)` — different functions.
The "val" feature set overlapped the real val fold by only 20%, and a fifth of val leaked
into training. Symptom: macro-F_0.5 0.214 against AUC 0.9985, a gap too large to be
anything but wiring. Fixed by deriving the fold in scoring.py and registering the id list
with DuckDB. **Never re-implement the split.** Both feature sets were recomputed.
